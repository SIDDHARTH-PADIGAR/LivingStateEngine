
# Evaluation Report

## Summary

The Living State Engine reconstructs project status from chronological events, including contradictory updates, unresolved risks, overdue commitments, and out-of-order arrivals.

Three synthetic benchmarks were run. All results below are from actual local executions. The expected statuses were hand-authored rather than generated by the engine.

## Results

| Benchmark | Labeled states | State engine accuracy | Latest-status baseline |
|---|---:|---:|---:|
| Original benchmark | 256 | 100% (256/256) | 75.00% (192/256) |
| Challenge benchmark | 48 | 100% (48/48) | 68.75% (33/48) |
| Held-out challenge | 52 | 100% (52/52) | 61.54% (32/52) |

### Held-out challenge: risk detection

Positive means the estimated or labeled state is `at_risk` or `blocked`.

| Metric | State engine | Latest-status baseline |
|---|---:|---:|
| True positives | 22 | 2 |
| False positives | 0 | 0 |
| True negatives | 30 | 30 |
| False negatives | 0 | 20 |
| Precision | 100% | 100% |
| Recall | 100% | 9.09% |
| F1 | 1.00 | 0.1667 |

The held-out benchmark contained 13 synthetic scenarios, 52 events, and 52 labeled state estimates. The engine had zero misclassified states in its first recorded run.

## What the results support

The engine handled the tested combinations of contradictory status reports, completion, overdue commitments, risk severity changes, issue resolution, and late-arriving events better than the latest-explicit-status baseline.

The held-out run provides additional evidence that the deterministic rules handle scenarios beyond the original repeated templates.

## What the results do not support

These benchmarks do not establish 100% real-world accuracy.

All scenarios were authored within this development process, and the expected labels may reflect the assumptions used to design the rules. The holdout was created separately from the original benchmark, but it was not independently collected or labeled by an external evaluator.

The datasets are small, synthetic, and not statistically representative of company projects. The baseline is also intentionally simple.

Matching an expected outcome to an actual outcome does not prove that a recommendation caused the result. Recommendation effectiveness has not been independently established.

No claims are made about production-scale latency, throughput, or generalization to real organizational data.

## Reproduction

Run from the repository root:

```powershell
.\.venv\Scripts\python.exe -m pytest -q

.\.venv\Scripts\python.exe scripts\generate_dataset.py
.\.venv\Scripts\python.exe scripts\evaluate_dataset.py

.\.venv\Scripts\python.exe scripts\run_challenge_benchmark.py
.\.venv\Scripts\python.exe scripts\run_heldout_benchmark.py
```

The scripts write their datasets, labels, manifests, and evaluation results under `data/synthetic/`.

## Freeze decision

The current implementation is frozen at the reported rule set for this evaluation. No rules or labels should be changed to improve the reported held-out result.

Any future change to the state engine should trigger a fresh test run and a documented evaluation. Existing held-out results should remain preserved as a historical record.
